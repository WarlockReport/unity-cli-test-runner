# ADR-0010: クラス名解決時の部分一致誤検知（境界を考慮しないgrepによる別クラスの巻き込み）

## Status

Accepted (2026-08-22)

## Context

[ADR-0009](0009-oneshot-retry-for-test-launch-calls.md) の実機検証（別プロジェクトで、意図的に
1件failするよう仕込んだテストクラスを実行）の結果、`unity-test-runner` サブエージェントの最終報告が
「`list_tests` で確認された候補数と、実際に実行された件数が食い違う（一部が何らかの理由で除外された）」
という、実際には存在しない異常を報告していた。

調査の結果、以下が判明した（説明のため、対象クラス名を `FooTest`、衝突した無関係クラス名を
`BarFooTest` と一般化して記述する）:

- `FooTest` クラス自体の `[Test]` メソッド数は、ソースファイルを直接確認して確定した実数より
  多くカウントされていた
- `unity cmd list_tests --mode <Mode> --json` の生データに対し、クラス名 `FooTest` を**単純な
  部分一致（`contains`）でgrep**すると、`FooTest` 自身のメソッドに加え、無関係な別クラス
  `BarFooTest`（クラス名の末尾が `FooTest` と一致するだけ）のメソッドまで混入していた
- 一方、実際の `run_tests --filter_type testName --filter FooTest` 呼び出しはUnity側で厳密な
  クラス名一致をしていたため、実行結果自体（Pass/Fail件数）は正しかった

つまり、**テスト実行そのものにバグは無かったが、SKILL.mdステップ2の候補解決手順（`list_tests`の
出力を「ローカルでgrep」して候補を絞り込む）が単純な部分一致を許容する書き方になっており、これが
ステップ6の期待件数比較（`list_tests`で確認した対象数と実行結果の件数を照合する）を狂わせ、実際には
発生していない「実行漏れ」をエージェントに誤って報告させた。**

この種のクラス名の部分文字列衝突（`XxxYyy` というクラス名が別の `Yyy` というクラス名と接尾辞一致する）
は一般的なあるあるパターンであり、今回はたまたまUnity側のfilterが厳密一致だったために実害が
執行結果に出なかったが、候補解決とfilter適用が別の実装（一方はエージェントのローカルgrep、
他方はUnity Test Framework側のfilter実装）である以上、両者の一致基準が常に同じである保証はない。
ステップ2の候補解決自体を境界考慮なしのまま放置するのは、将来的に実行結果そのものを誤らせる
リスクを残す。

## Decision

SKILL.mdステップ2の「クラス名・アセンブリ名・自然言語で渡された場合」の候補絞り込み手順に、
クラス境界を考慮した一致を必須とする指示を追加した。

- `FullName` は `Namespace.ClassName.MethodName` の形式でドット区切りであることを踏まえ、
  `ClassName` の前後がドット（または文字列の先頭）で区切られているかを確認する一致方法を明記した
  - jq例: `select((.FullName | split(".")) as $p | $p[-2] == $c)`（`FullName`を`.`で分割し、
    末尾から2番目の要素＝クラス名部分が完全一致するかを見る）
  - grep例: `\.ClassName\.`（前後にドットを含むパターンでマッチさせる）
- 既知の罠に、今回発見した具体事例（`FooTest` と `BarFooTest` の衝突）を記録した

この修正は候補解決（ステップ2・ステップ6の期待件数照合）のみに関わり、実行そのもの
（`run_tests`/`run-editmode-test.sh`等）の呼び出し方は変更していない。

## Consequences

- クラス名がグローバルに一意でない（別クラス名の接尾辞になっている）ケースでも、ステップ2の候補数と
  ステップ6の実行結果件数が一致するようになり、今回のような「実際には起きていない実行漏れ」の誤報告を
  防げる
- クラス境界を考慮してもなお複数クラスにまたがる場合は、既存のステップ2「上記以外で対象を一意に
  絞れない複数件」のルール（候補一覧を提示してユーザーに確認）がそのまま適用される。今回のケースは
  境界を正しく考慮すれば候補が `FooTest` のメソッドのみに絞られるため、このルートには乗らない
- `run_tests --filter_type testName` 側のfilter実装が本当に常に厳密一致であるという保証を実機で
  網羅的に検証したわけではない（今回の1事例で確認できたのみ）。ステップ2側を厳密化したことで、
  仮にfilter側の挙動にも将来的なばらつきがあったとしても、少なくとも候補提示・件数照合の段階で
  食い違いに気づける
