# ADR-0030: `unity` CLI 1.0 の結果だけの出力と、終了コードを主にした失敗の分類

## Status

Accepted (2026-11-13)

## Context

`unity` CLI 1.0.0 と `com.unity.pipeline` 1.0.0（2026-11-11、初の安定版）が出た。TestProject（Unity 6000.3.25f1）で実測した。

**壊れる主因は CLI の出力形式の変更だった。** CLI 1.0.0-beta.16 以降の `unity cmd ... --json` は、出力を整形する Editor に対して
`success`/`command`/`data`/`target` のエンベロープを付けず、**コマンドの結果だけ**を出す（CLI の changelog: "against an Editor that formats
its output, unity command --format json prints the command's result without the success, command, parameters and target envelope"）。
エンベロープを戻すオプションは無い（`--result-only` は従来から結果だけ）。Pipeline 0.10.0-exp.1 でも同じ形になることを確かめた。
つまり CLI を 1.0 に上げた時点で、`.data.result` を読む v0.10.0 のプラグインは動かない。

実測した CLI 1.0.0 の振る舞い（Pipeline 1.0.0）:

| 状況 | 終了コード | 標準出力 | 標準エラー |
| --- | --- | --- | --- |
| 成功（単一の結果） | 0 | 結果のオブジェクトだけ | 空 |
| 成功（配列の結果: 同期 `test run`・`test list`） | 0 | 1 行 1 オブジェクト | 空 |
| `test run --async-tests` の受理 | 0 | 空 | 空 |
| 失敗テストを含む `test status` の完了 | 6 | ステータス | `error: 1 of 3 tests failed: ...` |
| 一致 0 件の `test status` の完了 | 2 | ステータス（`summary.total: 0`） | `error: No selected tests found.` |
| 自前コマンドの `success:false` | 6 | 結果 | 空 |
| コマンドが無い（旧名を含む） | 13 | 空 | `No command named '...' is available. ...` |
| 引数名の不一致 | 2 | 空 | `test run has no parameter --filter_type. Did you mean --filter-type?` |
| ドメインリロード中の切断 | 6 | エンベロープ `COMMAND_FAILED`、`the Editor closed the connection without answering ...`（または `... before the command finished; it may not have run`） | 空 |
| エディタが見つからない（リロード中の瞬断を含む） | 12 | エンベロープ `EDITOR_NOT_RUNNING`、`No Pipeline instance found for project: ...` | 空 |
| 存在しないプロジェクトパス | 11 | エンベロープ `NOT_A_PROJECT` | 空 |

- CLI 側のエラーだけが `{success:false, command, data:null, errors:[{code, message}]}` のエンベロープで標準出力に出る。
  コマンドの結果は `data` キーを持たないので、`success == false and data == null and errors が配列` で区別できる
- CLI の changelog によると、busy（読み込み・コンパイル・リロード中、同時実行の上限超過）は終了コード 17（`EDITOR_BUSY`）、
  モーダルダイアログは終了コード 18（`EDITOR_BLOCKED_BY_DIALOG`）、タイムアウトは 14。17 は再現できず未実測。
  **シーン更新の確認ダイアログが開いている間の `editor status` は 18 ではなく 14（タイムアウト）だった**（Unity 6000.3.25f1。
  標準出力は空、標準エラーに `error: 'editor status' did not complete within its 10 s timeout. ...`）。`script recompile_status` は
  応答し続けた。Unity 6000.3 ではダイアログの追跡が働かないという 0.9 時点の観測（SKILL.md ステップ0）と一致する
- 古い CLI（1.0.0-beta.13）と Pipeline 1.0 の組み合わせでは、エンベロープは残るが、失敗テストを含む `test run` が
  `data:null` と 1 行のエラー文だけになり、失敗のメッセージとスタックトレースが失われる

既存スクリプトをそのまま CLI 1.0 + Pipeline 1.0 で動かすと、`run-tests-batch-editmode.sh` 以外は誤った終了コードを返した
（`check-editor-ready.sh` 2、`ensure-compile-clean.sh` 3、`run-editmode-test.sh` 2、PlayMode 系 2、絞り込み 1）。

## Decision

1. **`unity` CLI 1.0.0 以降専用にする**（Pipeline も 1.0.0 以降専用。[ADR-0031](0031-test-results-single-camelcase-shape.md)）。
   0.10 用の応急版（v0.10.1）は出さない。0.10 の利用者には「CLI を 1.0.0-beta.15 以前に戻す（`unity self-update --rollback`）か、
   Pipeline 1.0 + v1.0.0 に上げる」と案内する
2. **`_lib.sh` は標準出力・標準エラー・終了コードを分けて取り込む**（`UNITY_CMD_OUT` / `UNITY_CMD_ERR` / `UNITY_CMD_DIAG` / `UNITY_CMD_RC`）。
   パースは標準出力だけ、分類は終了コードと両方の文言で行う
3. **`run_unity_cmd_resilient` の分類**（上から順に判定）:
   - 終了コード 0 → 成功。ただし標準出力が旧 CLI のエンベロープ（`.data.command` を持つ）なら版のずれ（3）
   - 終了コード 18（または `EDITOR_BLOCKED_BY_DIALOG`）→ ダイアログ（新設の戻り値 4。リトライしても解消しないので即返す）
   - 終了コード 13、`No command named` / `Command Not Found` / `has no parameter --` → 版のずれ（3）
   - 一時的失敗（予算内でリトライし、超えたら 2）: 終了コード 12（`EDITOR_NOT_RUNNING`）、17（`EDITOR_BUSY`）、
     `the Editor closed the connection`、従来の到達不能・busy・429 の文言
   - それ以外 → 一時的でない失敗（1）。**終了コード 6 の結果（失敗テストを含む完了、`success:false`）もここに入る**ので、
     呼び出し元は 1 でも標準出力の中身を読んで判断する。標準出力が空なら標準エラーを返し、理由（一致 0 件・値の誤り等）を判定・表示できるようにする
4. 呼び出しは `$(...)` のサブシェルで行われ、`UNITY_CMD_RC` は呼び出し元に届かない。そのため版のずれの種類は
   `exit_on_version_mismatch` が**応答の中身**で見分けて案内文を変える（旧 CLI のエンベロープ → CLI を上げる、
   PascalCase の自前コマンド応答 → UPM パッケージを上げる、それ以外 → 3 つの版を揃える）
5. `extract_result_payload` は「標準出力全体が JSON のオブジェクトか配列 1 個ならそれ」を返す。`.data.result` と二重エンコード文字列の
   読み取りは削除し、CLI 側のエラーのエンベロープは結果として返さない。`test list` は `jq -s` で配列にまとめて読む
6. ダイアログ: `ensure-compile-clean.sh` は終了コード 18 で即 exit 4、`check-editor-ready.sh` は exit 1、テスト実行スクリプトは exit 2
   （標準エラーに「ダイアログ」）。従来の非対称性（`script recompile_status` だけが応答する）による判別はフォールバックとして残す

## Consequences

- CLI 1.0 より古い CLI では、どのスクリプトも「unity CLI を 1.0.0 以降に上げる」案内を出して終了コード 3 で止まる
- `unity cmd` を手で叩くとき、終了コード 6 / 2 は「失敗」とは限らない（結果は標準出力にある）。SKILL.md の「既知の罠」に記載した
- 終了コード 17 / 18 / 130 は changelog 由来で、分類には入れたが実測していない（18 は Unity 6000.3 では返らなかった。より新しい Unity で
  ダイアログの追跡が働く場合に備えて残す）。ダイアログの判別は、引き続き非対称性（`script recompile_status` だけが応答する）が主な手段
- 終了コード 14（タイムアウト）は一時的でない失敗として扱い、呼び出し元の非対称性による判別に回る
- エンベロープの有無で CLI の版を見分けるので、CLI がまた出力形式を変えると版のずれとして止まる（黙って誤読はしない）

### 実地検証（2026-11-13、TestProject、Unity 6000.3.25f1 + `com.unity.pipeline` 1.0.0 + `unity` CLI 1.0.0）

- `check-editor-ready.sh` → 0。`ensure-compile-clean.sh` → 0（C# 変更ありで `codeLoadCount` 15 → 16 を確認）、
  構文エラーを入れて 1（`error CS1525` / `CS1002` を報告）、直して 0
- ドメインリロード中の `editor status` は、終了コード 6（`closed the connection`）→ 12（`EDITOR_NOT_RUNNING`）→ 0 と推移し、
  スクリプトは一時的失敗としてリトライして完了を待てた
- CLI の `--timeout` 超過は、テストの実行では再現できなかった（`--timeout 0` は値の誤りとして終了コード 2 で拒否される）
- シーン更新の確認ダイアログが開いている間（e2e の Pipeline 差し替え後に発生）: `editor status` は終了コード 14、`script recompile_status` は 0。
  `check-editor-ready.sh` は 1（ダイアログの案内）、`ensure-compile-clean.sh` は 4 を返した
- `e2e/run-all.sh`: 一致 58 件 / 不一致 0 件。`e2e/run-all.sh --pipeline 1.0.0`: 一致 58 件 / 不一致 0 件、後片付け成功
  （0.10 時点の 59 件から 1 件減ったのは、カンマ区切りの testName の罠の照合が「0 件の SUMMARY」から「終了コード 1」の 1 件になったため）
