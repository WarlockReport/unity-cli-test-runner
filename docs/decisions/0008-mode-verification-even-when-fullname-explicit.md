# ADR-0008: FullName明示時もMode裏取りを必須化（EditMode/PlayMode取り違え対策）

## Status

Accepted (2026-08-21)

## Context

SKILL.mdのステップ2「テスト対象の解決」には、「ユーザーから完全名（`FullName`）が明示された場合は、そのまま次へ進む」という分岐があった。
この分岐は、呼び出し元（人間の発言・plan文・コントローラーからのディスパッチ文など）が添えた `Mode`（EditMode/PlayMode）を確定情報として鵜呑みにする抜け穴になっていた。

plan文はテストクラスが実際にどちらのアセンブリ／基底クラスに属するかを実行時点まで正確に知り得ないため、古い/誤った前提のままModeを書いていることがある。
この状態でステップ5（実行）へ直行すると、指定Modeでの実行が失敗し、正しいModeでの再試行が必要になる。実際にこのパターンでEditMode/PlayModeを取り違えるケースが確認された。

これは「既知の罠」に記載済みの「`--filter_type testName` に複数完全名をカンマ区切りで渡すと `success:true` のまま `Summary.Total:0` で静かに空振りする」罠とも近い性質を持つ。
呼び出し元の指定を無条件に信頼すると、実行はエラーにならずに終わるが結果が意図と食い違う、という失敗モードである。

## Decision

`list_tests --mode <Mode> --json` の応答は `.data.result.Tests` が配列で、各要素が `{FullName, Mode, Assembly, Categories, Explicit}` を持つ（実地検証済み）。
この実データを「参考情報でしかない呼び出し元指定のMode」より優先する情報源として扱う。

SKILL.mdのステップ2を以下のように変更した。

- ユーザーから完全名（`FullName`）が明示された場合でも、そのまま次へ進まず、 `list_tests --mode EditMode`/`list_tests --mode PlayMode` の出力から当該 `FullName` に完全一致するレコードを探し、実際の `Mode` を確定する
  - 該当レコードが見つからない場合: 誤字や存在しないテスト名の可能性として報告し、実行しない
  - 呼び出し元が添えたModeと実際のModeが食い違う場合: 黙って実際のModeで上書き実行せず、その食い違い（指定Mode／実際のMode）をそのまま報告する。plan文等の記載が古い可能性を示すシグナルなので、実行を止めてユーザー/コントローラーに確認を仰ぐ
  - 一致した場合（またはそもそもModeが添えられていなかった場合）: 確定したModeでそのまま次へ進む

## Consequences

- FullName明示のケースでも必ず `list_tests --mode EditMode` と `list_tests --mode PlayMode` の両方を呼ぶことになる。
  そのため、従来「Mode確認をスキップできる最短経路」だった分だけ、ステップ2の呼び出し回数が増える（既にクラス名・自然言語指定のケースでは同じ2回の呼び出しを行っていたため、全体としての呼び出しパターンは統一される）
- 呼び出し元のModeと実際のModeが食い違った場合は実行を止めて報告する運用になるため、古いplan文に基づく誤った自動実行を早期に検知できる。
  一方、正当な理由でMode表記が省略／簡略化されていたケースでも一旦立ち止まる（安全側に倒す判断）
