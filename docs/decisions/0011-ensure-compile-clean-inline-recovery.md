# ADR-0011: `ensure-compile-clean.sh`のポーリング予算超過に対するスクリプト内自動リカバリ

## Status

Accepted (2026-08-22)

## Context

実プロジェクトのセッションで `unity-test-runner` を6回ディスパッチしたところ、4回は初回で問題なく成功し、2回で一時的な停止（ハング）が発生した。
いずれも「最終レビュー修正の検証」段階、直前のテスト実行からすぐ再実行を依頼したタイミングで、`ensure-compile-clean.sh`（[3/5] `recompile_status` ポーリング、または[4/5] `editor_status` によるドメインリロード完了の安定確認）がポーリング予算（既定60秒）超過により `exit 2` を返した。

いずれのケースも、コントローラーが直後に `unity cmd editor_status` を直接叩いて確認したところ `{"status":"ready","compiling":false,"domainReloadInProgress":false}` で実際には正常（モーダルダイアログもなし）であり、同じ内容で再ディスパッチしたところ両方とも即座に成功した。

これは [ADR-0007](0007-domain-reload-transient-pipeline-unreachable.md) で対策した「ドメインリロード中の一時的なPipeline切断」と同根の事象と考えられる。
ADR-0007の恒久修正（一時切断を寛容に扱うポーリング継続、`editor_status`の2回連続安定確認）自体は今回も正しく機能しており、誤った成功報告や誤った失敗報告は一度も無かった。
ADR-0007の設計は「ハングを完全に無くす」のではなく「盲目的な無限リトライをせず、安全に呼び出し元へ委譲する」ものであり、その点は意図通りだった。

ただし、ADR-0007は一時切断の継続時間を「ドメインリロードの1〜2秒」と想定していたのに対し、今回は既定60秒の予算をも超える、より長い一時切断が実運用で2/6の頻度で発生した。
この想定超えの継続時間自体は許容せざるを得ないが、問題は**回復確認の主体**にあった。
現状の設計では、スクリプトが `exit 2` を返した後の「直接確認→回復していれば再実行」という判断をコントローラー（`unity-test-runner` サブエージェントをディスパッチする側）に委ねていた。
これはサブエージェントの1ターンが終了してコントローラーへ報告が返り、コントローラーが確認した上で同一内容を再ディスパッチする、という往復を要求する設計であり、今回のように「実際には数秒後に回復している」ケースでも毎回この往復コストがかかってしまう。

## Decision

`ensure-compile-clean.sh` のステップ3・ステップ4のポーリングロジックを関数化した上で、予算超過時にコントローラーへの報告・往復に頼らず**スクリプト内で完結する1回限りの自動リカバリ**を追加した。

- ステップ3・ステップ4それぞれが予算超過（かつ`unity cmd`自体の非一時的なハード失敗ではない場合）に到達すると、まず `unity cmd editor_status --json` を直接確認する。
  この確認自体がたまたま一時切断のタイミングに重なって「未回復」と誤判定しないよう、既存の `run_unity_cmd_resilient`（一時切断のみ最大15秒リトライする、他の単発コマンドと同じイディオム）を使う
  - `compiling:false` かつ `domainReloadInProgress:false` が確認できなければ、回復未確認として、そのまま `exit 2`（追加の待機・リトライはしない。真のハングとして扱う）
  - 確認できれば「回復済み」とみなし、該当ステップのポーリングを新しい予算で**1回だけ**やり直す（無限ループ防止のため1回限定。やり直しでも予算超過した場合は`exit 2`）
- `unity cmd` 呼び出し自体が非一時的な理由（transient unreachable以外）で失敗した場合は、この自動リカバリを試みず即座に `exit 2` とする（回復の見込みが薄いケースに時間を浪費しない）
- 呼び出し元（コントローラー・`unity-test-runner`サブエージェント）が予算を明示的に大きく取りたい既知のケース（複数ファイルにまたがる大きめの修正の直後など）向けに、
  既存の第1引数（ポーリング予算秒数の上書き、既定60秒）を積極的に使う指針をSKILL.mdに追記した

SKILL.mdの「ハング・タイムアウト時の対応」節にも、スクリプトが`exit 2`を返した時点で既に上記の自動リカバリを内部で試行済みであることを明記し、
呼び出し元が追加で直接確認や無条件の再実行を行う必要がないことを明示した。

## Consequences

- 今回観測したような「予算超過直後に直接確認すれば実は回復済み」というケースは、コントローラーへの報告・再ディスパッチという往復コストをかけずにスクリプト内で自己解決するようになる
- 最悪ケースの所要時間は、各ステップが1回の自動リカバリ（フレッシュな予算で丸ごとやり直し）を試みうるため、
  指定した予算秒数の最大4倍強になりうる（既定なら最大240秒＋直接確認分。直接確認は`run_unity_cmd_resilient`で一時切断のみ最大15秒リトライするため、2ステップ分で最大30秒程度が上乗せされうる。従来は最大120秒）。
  これは「回復が裏取りできた場合のみ」の1回限りのリカバリであり、`unity cmd`自体のハード失敗や、直接確認でも回復していないケースでは追加の待機なしに即 `exit 2`となるため、真のハング検知が大きく遅れることはない
- リカバリの判定は `unity cmd editor_status` の直接確認に基づく。
  この確認自体を素の単発呼び出しにすると、確認のタイミングがたまたま一時切断に重なった際に「未回復」と誤判定し、
  往復コスト削減の効果が薄れる（元の2/6の事象が確認フェーズに移動するだけになる）ため、確認自体も`run_unity_cmd_resilient`（一時切断のみの有限リトライ）で行う
- モック`unity` CLIを用いたシナリオテスト（正常系／ステップ3リカバリ成功／ステップ3未回復による早期`exit 2`／
  非一時的ハード失敗による即`exit 2`／ステップ4リカバリ成功／直接確認は回復済みだが、リトライ後も予算超過、の6パターン）で、
  意図した終了コード・所要時間になることに加え、
  「直接確認で回復未確認のため未実施」と「リカバリを試みたが失敗」の2つの失敗モードが標準エラー出力のメッセージ上でも矛盾なく区別できることを確認した
- `run-playmode-test.sh`/`run-tests-batch-playmode.sh`/`check-editor-ready.sh` には同種の自動リカバリを導入していない。
  今回の実測で`exit 2`が観測されたのは`ensure-compile-clean.sh`のみであり、YAGNIの観点からエビデンスのある箇所のみを修正した。
  他スクリプトで同様の事象が確認された場合は改めてADRを起票して対策する
