# ADR-0014: テスト結果報告の機械導出化（サブエージェントの二重報告・楽観的幻覚への対策）

## Status

Accepted (2026-09-21)

## Context

`wr-unity-cli-tools:unity-test-runner` サブエージェント（いずれも `model: haiku` を
コントローラーが明示指定）が、1回のディスパッチに対して
SubagentHandback を2回返す事象が3件連続で観測された。コントローラーから当該エージェントへ
追加のメッセージを送って再開させた事実はなく、いずれも自発的な二度目の停止である。トランス
クリプトを検証したところ、Unity CLI が返したツール出力（テスト結果JSON）は3件とも正しかった。
壊れていたのはテスト実行ではなく最終報告の生成であり、先に届いた報告（報告A）が自分自身の
ツール出力と矛盾する内容を書いていた。

- ケース1: 報告Aが合計42件、報告Bが87件（実際も87件）。
  トランスクリプト内のテスト結果JSONは `"passed": 87, "failed": 0` のみで、42という数値は
  テスト件数としてはどこにも出現しない
- ケース2: 件数は両報告とも87件で一致したが、報告Aが列挙した
  6つのテストメソッド名がトランスクリプトに1件も出現せず、意味の近い日本語へ言い換えられて
  いた。実在する名前は各6回出現しており、エージェントは正しい名前をツール出力として受け取って
  いたうえで言い換えて報告した
- ケース3: 報告Aが「合計89・Pass89・Fail0（全件PASS）」、
  報告Bが「合計89・Pass88・Fail1」。トランスクリプト内のJSONは `"passed": 88, "failed": 1` の
  みで、`"passed": 89` はどこにも出現しない。実在するFAILは特定のテストクラスに属し、
  例外は `System.NullReferenceException` であり、プランの実在の
  不具合に由来していた。後で届いた報告Bが3件とも正しく、報告Aは一貫して楽観方向
  （件数多め・Failが消える・テスト名がもっともらしい別名）に食い違っていた

3例に共通する誘因として疑わしいのは、コントローラーのディスパッチ文に書かれた期待値
（「全件PASS」「6本」「89件になっているはず」等）である。報告Aの内容はいずれもこの期待値と
一致していた。3例とも `model: haiku` であり、同セッションで `sonnet` 指定だった実装・レビュー
エージェントでは二重報告は発生していない。

さらに、この修正プラン自体の実行中にも、対策対象と同型の「総合結果の数値だけが実データから
乖離する」事象が2回、別の文脈（`unity-test-runner` サブエージェントではなく、SDDの実装サブ
エージェント `haiku`）で再現している。

- 実装者（haiku）が完了報告で「全8ケース」と書いたが、実際のテスト
  ケース数は10件だった。個別タスクの出力自体は正確で、総合結果の見出しだけが実データと
  乖離していた
- 実装者（haiku）が「ケース1-9 計9件」と書いたが、実際のケース数は
  11件（1b・1cが抜けていた）。これも個別出力は正確で、総合結果の数値だけが乖離していた

どちらも成果物（コード・テスト自体）への影響はなく、報告ファイルの数値記述のみが誤っており、
レビューで訂正済みである。これにより、当初観測した事象を「`unity-test-runner` サブエージェント
固有の不具合」と狭く捉えるのではなく、「サブエージェントの最終報告が、実データではなく期待値へ
引き寄せられて楽観方向に乖離する」という、より一般的な傾向として扱う根拠が得られた。

未解決事項: 二重報告がなぜ起きるかは不明である。
依然として `haiku` 系エージェントでのみ観測されており、 `sonnet` での再現有無は未検証のままである。

## Decision

二重報告自体はハーネス側の事象であり、本リポジトリからは直せない。したがって狙いを
「二重報告を起こさないこと」ではなく「**2回来ても内容が食い違わないようにすること**」に
定めた。同じ結果JSONから機械的に導出された報告であれば、生成が何回発生しても同一の文字列に
なるはずであり、二重報告そのものが無害化される。

加えて、今回破られたのは「言葉による禁止」（ディスパッチ文・SKILL.mdでの「要約せず正確に
報告せよ」といった指示）だったため、対策を指示文の強化だけに頼らず、報告文そのものを
`skills/unity-cli-test-runner/scripts/summarize-test-result.sh` に生成させる方式に切り替えた。
このスクリプトは結果JSONから `SUMMARY` / `FAIL` ブロック群 / `SOURCE`（生JSONの絶対パス）を
機械的に組み立てて標準出力へ出し、サブエージェント（`agents/unity-test-runner.md`）はこの
標準出力をそのまま逐語で報告に貼るだけの役割に限定した。自然語による要約・言い換えの余地を
報告生成の経路から排除している。

併せて以下も決定した。

- ディスパッチ文・SKILL.mdの期待値（「全件PASSのはず」等）を報告の根拠にしないことを明記する。
  期待値の記述自体が3例に共通する誘因として疑われたため
- サブエージェントの `model` を `haiku` から `sonnet` に変更する（`agents/unity-test-runner.md`）。
  同セッションの `sonnet` 指定エージェントでは二重報告・楽観的乖離のいずれも発生していない
  という観測に基づく緩和策であり、原因の特定ではない
- サブエージェント方式そのものは維持する。大量のツール出力をコントローラーのコンテキストから
  遠ざける利点があるため、方式ごと廃止するのではなく報告生成の経路だけを機械化する

## Consequences

- 報告は自然語要約からJSON由来の逐語貼付に変わり、トークン消費は増える。ただし増えるのは
  FAILが存在する場合（`FAIL` ブロックが出力される場合）に限定され、全件PASS時は `SUMMARY` 行
  中心の短い出力にとどまる
- `SOURCE` 行により、コントローラーは疑わしい場合に `jq` で生JSONを安く裏取りできる
- `summary` を結果JSONの想定パスから取り出せない場合、スクリプトは `exit 3` を返し標準出力には
  `SOURCE` 行のみを出す契約にした。これにより「0件」「全件PASS」という最悪の誤報告が構造的に
  発生しなくなった（値を推測して埋める経路そのものが無い）
- `summary.failed` と `results[]` 内の実際のFailed件数が食い違う場合、`MISMATCH` 行を出力する
  ようにした。結果JSON自体が不完全である可能性を報告の時点で可視化する
- フィクスチャベースの回帰テスト `tests/summarize-test-result.test.sh` を追加した。これは
  このリポジトリで初めて導入された自動テストである
- 本ADRの対策は「報告文の生成を機械化することで二重報告を無害化する」ものであり、二重報告
  それ自体の発生機構には対処していない。`sonnet` への変更も観測に基づく緩和策であり、原因の
  特定・修正ではない
- 未解決: 二重報告の発生機構は不明のままである。`sonnet` でも同種の事象が起きるかは今後の
  観測による。段1実行中に観測したSDD実装サブエージェント（`haiku`）2件の乖離は、対象が
  `unity-test-runner` ではなくテスト実行を伴わない完了報告だったため、本ADRの対策
  （`summarize-test-result.sh` の逐語貼付）の適用範囲外である。同種の傾向が他のサブエージェント
  報告一般に及ぶのであれば、SDD側の完了報告についても機械導出化の要否を別途検討する必要がある

## 実地検証（2026-09-21）

実運用中の対象プロジェクト、Unity `6000.3.14f1`（`unity cmd editor_status --json` 実測）で以下を確認した。
`com.unity.pipeline` は段1の前提どおり0.6系のまま。以下では検証に使ったEditMode対象クラスを `<EditModeクラス>`、
PlayMode対象クラスを `<PlayModeクラス>` と表記する。

- `check-editor-ready.sh` → 終了コード0、`status` は `ready`
- EditMode（`run-editmode-test.sh <EditModeクラス> testName 120`）→
  `summarize-test-result.sh` の出力は `SUMMARY mode=editmode total=5 passed=5 failed=0
  skipped=0 inconclusive=0 duration=9.29`、`MISMATCH` 行なし、終了コード0。同一結果JSONに対する
  `jq -c '.data.result.Summary'` は `{"Total":5,"Passed":5,"Failed":0,"Skipped":0,
  "Inconclusive":0}` で、`SUMMARY` 行の数値と完全一致した
- PlayMode（`run-playmode-test.sh <PlayModeクラス> testName 300 300`）→ `summarize-test-result.sh`
  の出力は `SUMMARY mode=playmode total=3 passed=3 failed=0 skipped=0 inconclusive=0
  duration=0.01`、終了コード0。同一結果JSONに対する `jq -c '.summary'` は `{"total":3,"passed":3,
  "failed":0,"skipped":0,"inconclusive":0}` で完全一致した
- `wr-unity-cli-tools:unity-test-runner` サブエージェント（`agents/unity-test-runner.md` の
  `model: sonnet` 設定）へ、EditMode・`<EditModeクラス>`・`testName` の実行を、件数や合否の
  期待値を一切書かずにディスパッチした。返ってきた報告には `SUMMARY mode=editmode total=5
  passed=5 failed=0 skipped=0 inconclusive=0 duration=9.67` と `SOURCE <絶対パス>` が逐語で
  含まれ、実際の再実行結果（上記EditModeの数値）と一致した。自然語での言い換え・期待値の
  記載は無かった。SubagentHandbackは1回のみで、`temp/` 配下の一次調査記録で観測したような
  二重報告は今回は再現しなかった

以上により、Task 1〜8 の成果（`summarize-test-result.sh` の数値算出、`agents/unity-test-runner.md`
の機械導出手順、`model: sonnet`）が実機のEditMode/PlayMode両方で契約どおりに機能することを確認
した。二重報告の再現有無・`sonnet`での長期的な安定性は、今回の1回の観測だけでは判断できず、
引き続き未解決事項として扱う。
